## はじめに

自作の資産管理アプリで、こんな設計にしていた。

> 株式の保有口数や現金残高は、テーブルに持たない。**取引履歴（台帳）から毎回計算で導出する。**

「今 100 株持っている」という状態をカラムに保存せず、`BUY 60` と `BUY 40` という 2 行の取引から `derivePosition()` が 100 を計算する、という作りだ[^1]。真実の源泉を台帳ひとつに保つ、素直な設計に思えた。

[^1]: なぜ状態を保存せず導出するのか、という設計判断そのものは本題から外れるので割愛する。以前に書いた [「口数ゼロなのに取得原価 1 円？」](https://zenn.dev/keisukenaito/articles/ghost-cost-basis-rounding) という取得原価の丸めの記事も、この「台帳から導出する」設計の上で起きた話だった。

ところがこの設計には、書き込み側にひとつ落とし穴がある。**不正なデータを 1 行登録してしまうと、その瞬間ではなく、後で別の画面を開いたときにアプリ全体が壊れる**のだ。

本記事は、その落とし穴を「検証ロジックを新しく書く」のではなく「**導出関数をそのまま検証器として使い回す**」ことで塞いだ話である。イベントソーシングや、write model と read model を分ける設計にも通じる考え方だと思う。

## 前提: 導出関数は「あり得ない状態」で例外を投げる

保有を導出する関数は、こういう形をしている。取引を日付順に処理して、口数と取得原価を積み上げるだけだ。

```ts
export function derivePosition(transactions: readonly TransactionInput[]): Position {
	const ordered = transactions.toSorted(
		(a, b) => a.occurredAt.getTime() - b.occurredAt.getTime()
	);

	let quantity = 0;
	let costBasis = 0;

	for (const tx of ordered) {
		switch (tx.type) {
			case 'BUY':
				quantity += tx.quantity;
				costBasis += tx.amount;
				break;
			case 'SELL':
				// 持っている以上に売ることはできない
				if (tx.quantity > quantity) {
					throw new Error(
						`SELL quantity ${tx.quantity} exceeds current holding ${quantity}`
					);
				}
				// ...取得原価を按分して取り崩す...
				quantity -= tx.quantity;
				break;
			// ...
		}
	}

	return { quantity, costBasis };
}
```

ポイントは `SELL` のガードだ。**保有 100 株に対して 150 株の売却があったら、黙って口数をマイナスにせず例外を投げる。** 現金残高を導出する `deriveCashBalance()` も同様に、残高を超える出金（WITHDRAW）で例外を投げる。

これは意図的な設計で、いわゆる **fail fast**（想定外の状態は握りつぶさず即座に落とす）である。金融データで「口数がマイナス」のような状態を黙って通すと、気づかないまま間違った数字を表示し続けることになる。それより、あり得ない状態には確実に気づけるほうがいい。

## 落とし穴: 原因の行を入れた「瞬間」は何も起きない

fail fast は健全な方針だが、状態を持たず毎回導出する設計と組み合わさると、厄介な形で牙をむく。

登録フォームに検証がなく、売り越しの `SELL` が 1 行 DB に入ったとしよう。このとき何が起きるか。

- **登録した瞬間**: 何も起きない。`INSERT` が成功するだけで、画面は正常に見える
- **次に資産一覧を開いた瞬間**: 一覧の読み込みは全取引を `derivePosition()` に通す。そこで初めて例外が飛び、**画面全体が 500 エラーで開けなくなる**

つまり **原因（不正な行の登録）と発症（一覧が落ちる）が、時間的にも画面的にも離れている**。しかも私のアプリには取引の削除 UI がまだないので、一度こうなると DB を直接触らないと復旧できない。「間違った数字が出る」より一段たちの悪い、「アプリが開けなくなる」障害である。

> これは状態をテーブルに保存する設計なら起きない。保存型なら「残高カラムがマイナスになる」だけで、静かに壊れて表示は出続ける。台帳から導出する設計は**騒がしく壊れる**代わりに、**整合性を守る責任を書き込み時点に移す**必要がある、というトレードオフだ。

したがって、登録フォームの側で「この取引を入れても台帳は壊れないか？」を検証しなければならない。

## 素朴な検証案と、その穴（バックデート問題）

まず思いつくのは「**今の保有数と比べる**」検証だ。

```ts
// 素朴案: 現在の保有数を超える売却を弾く
const current = derivePosition(existingTransactions);
if (candidate.type === 'SELL' && candidate.quantity > current.quantity) {
	return '保有数を超えて売却することはできません';
}
```

一見よさそうだが、これは**過去の日付での登録（バックデート）**を通してしまう。

例えばこういう順序だ。

1. 7/10 に「100 株買った」を登録する（現在の保有 = 100 株）
2. あとから 6/20 に遡って「50 株売った」を登録する

この 50 株の売却は、現在保有 100 株 ≥ 50 株なのでチェックを通過する。だが導出関数は**日付の昇順**に処理するので、実際には次の順で計算される。

| 処理順 | 取引 | その時点の保有 |
| --- | --- | --- |
| 1 | 6/20 SELL 50 | 0 株から 50 株売る → **💥 例外** |
| 2 | 7/10 BUY 100 | （ここまで到達しない） |

6/20 の時点では 1 株も持っていない。**「今」と比べる検証では、過去の時点の整合性を守れない**のだ。正しくは「その取引が発生した時点の保有」で判定しなければならない。

各時点の保有を検証側でもう一度計算する…？ それはつまり、導出関数と同じロジックを検証側に書き直すということだ。二重実装は必ずいつかズレる。

## 解決: 検証とは「導出のシミュレーション」である

発想を変える。各時点の保有を正しく計算できる関数は、すでに手元にある。**導出関数そのもの**だ。

ならば検証は、こう書けばいい。

> **「既存の全取引 ＋ 登録候補の 1 行」を導出関数に通してみる。例外が飛ばなければ登録してよい。飛んだら、そのメッセージを検証エラーとして返す。**

```ts
export function checkLedgerInvariants(
	assetType: string,
	existingTransactions: readonly TransactionInput[],
	candidate: TransactionInput
): string | null {
	try {
		// 既存 + 候補で、実際に導出を「試してみる」
		const simulated = [...existingTransactions, candidate];
		if (assetType === 'CASH') {
			deriveCashBalance(simulated);
		} else {
			derivePosition(simulated);
		}
		return null; // 例外が出なければ整合性は保たれる
	} catch (e) {
		const detail = e instanceof Error ? e.message : String(e);
		return `台帳の整合性が崩れるため登録できません（${detail}）`;
	}
}
```

実際に DB へ書き込む前に、**メモリ上で「もし登録したら」を先に再生してみる**。導出が例外を投げるなら、それは「登録すると後で一覧が落ちる」ことの先取りだ。その例外を、500 エラーではなく登録前のフォーム検証メッセージへと変換する。

この方式には効きどころが 3 つある。

**1. 不変条件の実装が 1 箇所に保たれる**
「売り越し禁止」「残高超の出金禁止」というルールは、導出関数の中にしか書かれていない。検証側はそれを**呼び出すだけ**で、ルールを複製しない。もし複製していたら、将来ルールを変えたときに「導出は通すのに登録は弾く」「登録は通すのに一覧が落ちる」といった食い違いが生まれる。ルールの真実の源泉も、やはりひとつに保つ。

**2. バックデートも自動的に正しく判定される**
検証が導出と同じ関数を使う以上、時系列処理も完全に同一だ。候補を配列に足して導出関数に渡せば、関数が内部で日付順に並べ替えて各時点を評価してくれる。前章のバックデート問題は、検証側で何も特別扱いせずに解決する。

**3. fail fast の例外の「意味」が変わる**
まったく同じ `throw new Error(...)` が、呼ばれる場所によって役割を変える。一覧の読み込み中に飛べば「500 の原因」だが、登録前のシミュレーションで飛べば「ユーザーに見せる検証メッセージの素」になる。例外を防御の最終ラインとして書いておくと、それを前倒しで叩くだけで検証が手に入る。

## 細部: 同一日付の順序を表示側と揃える

ひとつ地味だが大事な detail がある。候補は配列の**末尾**に足している。

```ts
const simulated = [...existingTransactions, candidate];
//                                          ^^^^^^^^^ 末尾に追加
```

導出関数は `toSorted()` で日付順に並べるが、`toSorted()` は**安定ソート**なので、**同一日付の中では元の配列の並び順が保たれる**。候補を末尾に足すということは「同じ日付の既存行の“後”に処理する」という意味になる。

これは、実際に登録したあとで一覧を読むときの並び順（`id` の昇順 = 後から入れた行が後）と一致する。**検証時のシミュレーションと、登録後の実表示とで、導出結果がズレない**ようにするための配慮だ。同じ日に複数取引がある口座では、この順序が保有計算に効いてくる。

## 不変条件テストで守る

この設計の心臓は「導出関数の例外が、そのまま登録の可否を決める」という接続部分だ。ここはテストで固定しておく。

```ts
test('その時点で保有を超える売却は登録を拒否する（バックデート）', () => {
	const existing = [buy('2026-07-10', { quantity: 100 })];
	const candidate = sell('2026-06-20', { quantity: 50 }); // 買う前の日付

	const error = checkLedgerInvariants('STOCK_JP', existing, candidate);
	expect(error).not.toBeNull();
});

test('現在保有の範囲内でも、過去時点で破綻するなら拒否する', () => {
	// 「今 100 株あるから 50 株売れる」を通してしまう素朴実装では、このテストが落ちる
	const existing = [buy('2026-07-10', { quantity: 100 })];
	const candidate = sell('2026-06-20', { quantity: 50 });

	expect(checkLedgerInvariants('STOCK_JP', existing, candidate)).not.toBeNull();
});

test('整合する取引は登録を許可する（null を返す）', () => {
	const existing = [buy('2026-06-01', { quantity: 100 })];
	const candidate = sell('2026-07-10', { quantity: 30 });

	expect(checkLedgerInvariants('STOCK_JP', existing, candidate)).toBeNull();
});
```

2 番目のテストは、この記事の主張そのものだ。**「現在の保有と比べる」素朴実装では絶対に通らない。** 検証の正しさが、テストとして言語化されている。

## 一般化: 「もう一度計算し直す」設計との相性

この「導出関数を検証器に転用する」手口が成立したのは、そもそも**状態を保存せず、履歴から毎回計算し直す**設計だったからだ。

- 状態を保存する設計なら、検証は「保存された残高カラム」を見ればよく、その代わり残高カラムと履歴の整合を別途保証する責任が生まれる
- 状態を導出する設計なら、整合性の責任は「導出が例外を投げないこと」に集約される。だから**その例外検査をそのまま書き込みバリデーションに使える**

これは、イベントソーシングで「コマンドを適用してみて集約が不変条件を破らなければ受理する」という発想や、CQRS で write model 側が整合性を担保するという役割分担と、地続きの考え方だと思う。大げさなフレームワークを持ち込まなくても、「派生状態を計算する純粋関数」がひとつあれば、その関数は**表示にも検証にも二役で使える**。

## まとめ

- 状態を履歴から**導出**し、あり得ない状態で**例外を投げる**（fail fast）設計は、不正な 1 行が「登録の瞬間」ではなく「後で別画面を開いた瞬間」に全体を落とす、という落とし穴を持つ
- 「今の状態と比べる」素朴な検証は、**過去日付での登録（バックデート）**を取りこぼす。整合性は「その取引が起きた時点」で判定しなければならない
- 検証を新しく書かず、**導出関数に「既存 ＋ 候補」を渡してシミュレートする**。例外が飛べば登録を拒否し、そのメッセージを検証エラーに変換する
- こうすると、不変条件の実装も時系列処理も**導出関数 1 箇所**に保たれ、二重実装のズレが生まれない
- 「派生状態を計算する純粋関数」は、**表示と検証の二役**で使える。それが履歴から導出する設計の隠れた配当だ
