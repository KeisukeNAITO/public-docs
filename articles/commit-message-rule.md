# なぜコミットメッセージに気を配るのか

端的に言えば「今の私ではない誰かへ簡潔に製品を変化させた意図を伝えるため」と考える。
チームで開発しているならばチームメンバーであるし、OSS[^1]ならば、時間も場所も価値観も離れた誰かかもしれない。
いずれにしても **"未来の自分に伝える"** は、外せないポイントではないだろうか。
自分が作ったプロダクトである以上、未来でも説明責任が果たせるようにしたい。

[^1]: オープンソースソフトウェア

## うまく伝えるにはどうするのか

**"言いたいこと"と"伝えるべきこと"は似て非なるもの** ということは心にとめておきたい。
「伝えるべきことを、相手に合わせて伝える。」を優先すべきで、自分の言いたいことの優先度はその後でいいと考える。
よってまず **伝える相手に興味を持ち理解度を高める** ことが重要となる。
相手を知って好転する例を挙げれば、相手が一緒に開発しているチームメンバーで、ユビキタス言語[^2]を使えるパターンだろう。
相手の情報がない場合、汎用的な手段として **"コミットの単位を小さくして話題に集中してもらう(させる)"** ことだろう。
単純なことを多数こなす場合の労力は要素の足し算的だが、単純なことでも組み合わせて１件にまとめた場合の労力は要素の掛け合わせ的になるだろう。

[^2]: システム開発プロジェクトにおいて、開発者、ビジネスの担当者、エンドユーザーなど、プロジェクトに関わる全員が共有する共通の言葉。

## 種別を作る (見極め中)

「コミットの単位を小さくして話題に集中してもらう」の別視点で、製品の変化に関する種別を添えるコメントは好ましいと考える。
種別が見えることは製品の履歴を手繰るうえで、変更の影響度や参照者の興味のある修正点を見つけ出す手助けになるだろう。
また副次的にコミットログ自体がナレッジ/ノウハウの源泉になることを期待している。
ただしブランチ戦略によっては、ブランチ名をもって種別を説明する運用戦略もあり得るので、各々確認はとるべきだろう。

注釈的ではあるが、種別を作ることで後述するような悩ましい課題を作り上げてしまう場合もあるので、翻って **"種別を作らないことも選択肢にあってよい"** と考える。

# 現状考えるテンプレート (見極め中)


## メッセージのスニペット

>[種別] 概要
>
>理由/背景、どうしようとしたか

## 追加する接頭辞と趣旨

| # | 追加する接頭辞 | 趣旨 |
| ---- | ---- | ---- |
| 1 | feat | 新機能の追加 |
| 2 | fix | バグの修正 |
| 3 | docs | ドキュメントのみの変更 (更新忘れの対応などをイメージ) |
| 4 | style | 空白、フォーマット、セミコロン追加など (整形忘れの対応などをイメージ) |
| 5 | refactor | 仕様に影響がないコード改善 |
| 6 | perf | パフォーマンス向上関連 |
| 7 | test | テスト関連 (後からテストのみの追加などをイメージ) |
| 8 | chore | ビルド、補助ツール、ライブラリ関連 |

### 例

>[feat] 社員情報検索APIの検索キーに勤務地を追加したうえでユーザ一覧を表示させた。
>
>フロントエンド側で任意の社員情報を取捨選択させていたが性能が出ないため、バックエンド側で社員情報検索に勤務地の絞り込み機能を追加し性能向上させる。


Gitメッセージは製品のシステムの移り変わりを説明すべきと現状考えている。
もしビジネス的な意図と紐づけたい場合は、ブランチ名/チケット/バックログと組み合わせるなどプロジェクト毎で検討するべきだろう。

## 展望

まだ種別について、煮詰める余地があると考えている。
相応しい接頭辞の判断には見極めが難しいシチュエーションもあると考えている。
ビジネス的な意図はパフォーマンス(perf)にあるが、システム的には新機能の追加(feat)のような上記の場合は典型だろう。
仮説として、refactorの"仕様に影響がないコード改善"とはATDDのテストコードに変化がなければOKではないか。
また、perfのパフォーマンス向上とfeatの新機能の追加を分ける点は、BDDのテストコードが変化しなければperfと考えてOKではないかと考えている。
そもそも論として、このコミットヒストリーをどう使うか?がこの考え方を最終的に決めるのではないだろうか。
上記の考え方はかなりシステム的な文脈を重視したヒストリーの残し方だと認める。
逆にビジネス的なヒストリーとして残すならば、製品の顧客価値を高める活動にしかfeatの接頭辞を与えたいと思わない。
- システム的な文脈のヒストリーを振り返った時にfeatに対するrefactor,perfのヒストリー数比から、"技術的負債を抑えられている!"と考えたり
- ビジネス的なヒストリーを振り返ってfeat以外のログばかりなので、"チームに何か問題があり前進していないのではないか?"と考える

―――といったように、要は **"ヒストリーを製品の変遷認識以外でもどう使うか?という戦略"** で切り替えるべきだろう。
最初に挙げた "未来の自分に伝える" を超えた、ややマネージメント的な視点だ。
