# 起きたこと

自作の資産管理アプリで、株式の保有状況を「取引履歴から計算で導出する」仕組みを作っていたときの話だ。

ある銘柄を**全株売却**したはずなのに、画面にはこう表示された。

> 保有口数: 0 株　取得原価: 1 円

1 株も持っていないのに、取得原価だけが 1 円残っている。幽霊のような 1 円である。本記事ではこれを勝手に**幽霊原価**と呼ぶ。

バグの原因は「整数の割り算をどの順番でやるか」だった。数学的には同じ式なのに、**丸めるタイミング**によって結果が変わる —— お金の計算に限らず、整数演算をするすべてのプログラムに関係する話なので、具体例多めで紹介する。

# 前提 1: 移動平均法 — 買うたびに「平均の買値」を更新する

株や投資信託を何回かに分けて買うと、1 株あたりの買値はバラバラになる。そこで「全部でいくら払ったか（**取得原価**）」を管理し、売るときは**平均取得単価**（取得原価の合計 ÷ 保有口数）× 売却口数ぶんの取得原価を取り崩す、というのが**移動平均法**だ。

例えば:

1. 1 株を 100 円で買う → 取得原価 100 円・1 株
2. もう 1 株を 200 円で買う → 取得原価 300 円・2 株（平均取得単価 150 円）
3. 1 株売る → 平均取得単価 150 円 × 1 株分を取り崩し → 取得原価 150 円・1 株

「売った分だけ、平均取得単価ぶんの原価を減らす」。これだけである。

# 前提 2: なぜ金額を浮動小数点数で持たないのか

「平均取得単価 150 円」のような割り算をするなら、小数が使える `number` でよさそうに思える。しかし JavaScript（に限らず多くの言語）の浮動小数点数は、十進小数を正確に表せない。

```js
0.1 + 0.2; // => 0.30000000000000004
100 * 1.1; // => 110.00000000000001
0.3 === 0.1 + 0.2; // => false
```

1 回ならわずかな誤差でも、取引のたびに足し引きを繰り返す台帳計算では誤差が蓄積する。「残高が 110.00000000000001 円」は許されないので、お金の計算では**最小通貨単位の整数で持つ**のが定石だ（円ならそのまま整数、ドルならセント単位の整数）[^1]。

[^1]: DB 側に正確な十進型（`Decimal` など）があればそれも選択肢だが、私の環境（SQLite）には十進型がなく、整数一択だった。

ここで問題が生まれる。**整数で持つと、割り算のたびに丸めが必要になる**のだ。

# 幽霊原価を再現する

最小の再現例を示す。手数料込みで合計 100 円払って 3 株持っているとする（1 株あたり 33.33... 円。割り切れない状況は手数料や分割買付で普通に発生する）。

この 3 株を**全部売却**したとき、取り崩す原価を「平均取得単価 × 売却口数」で計算してみる。

```ts
const costBasis = 100; // 取得原価の合計
const quantity = 3; // 保有口数
const sellQuantity = 3; // 全部売る

// ❌ 単価を先に丸めてから掛ける
const unitCost = Math.round(costBasis / quantity); // 100 ÷ 3 → 33
const costOut = unitCost * sellQuantity; // 33 × 3 → 99

const remaining = costBasis - costOut; // 100 − 99 → 1 ← 幽霊！
```

| 手順 | 計算 | 結果 |
| --- | --- | --- |
| 平均取得単価を丸める | 100 ÷ 3 = 33.33... → 丸めて | 33 円 |
| 売却分の原価 | 33 × 3 | 99 円 |
| 残る取得原価 | 100 − 99 | **1 円** |

3 株全部売ったのに、丸めで切り捨てた 0.33... 円 × 3 株分 = 1 円が置き去りになった。これが幽霊原価の正体である。

# 直し方: 「割ってから掛ける」を「掛けてから割る」に変える

取り崩す原価は「取得原価の合計 × 売却口数 ÷ 保有口数」で計算する。式変形しただけで、数学的には**完全に同じ式**である。

```ts
// ✅ 掛けてから割り、丸めは最後に 1 回だけ
const costOut = Math.round((costBasis * sellQuantity) / quantity);
// (100 × 3) ÷ 3 = 100 → ちょうどゼロ
```

| 手順 | 計算 | 結果 |
| --- | --- | --- |
| 先に掛ける | 100 × 3 | 300 |
| 割って丸める | 300 ÷ 3 = 100 → 丸めて | 100 円 |
| 残る取得原価 | 100 − 100 | **0 円** ✅ |

違いは丸めるタイミングだけだ。

- **単価先計算**: 割り算 → **丸め** → 掛け算。丸め誤差が掛け算で**増幅**される（誤差 × 売却口数）
- **総額按分**: 掛け算 → 割り算 → **丸め**。丸めは最後に 1 回だけで、誤差は最大 0.5 円

実数の世界では `(a / b) * c` と `(a * c) / b` は同じだが、**丸めが挟まった瞬間に別の式になる**。これが本記事で一番伝えたいことである。

# もっと意地悪な例: 分割売却するとマイナス原価まで出る

全量売却だけの問題ではない。取得原価 1,000 円・7 株を、2 株 → 2 株 → 3 株と 3 回に分けて売ってみる。

**❌ 単価先計算（割ってから掛ける）:**

| 売却 | 平均取得単価の計算 | 取り崩し | 残口数 | 残取得原価 |
| --- | --- | --- | --- | --- |
| 2 株 | 1000 ÷ 7 = 142.86 → 143 | 143 × 2 = 286 | 5 | 714 |
| 2 株 | 714 ÷ 5 = 142.8 → 143 | 143 × 2 = 286 | 3 | 428 |
| 3 株 | 428 ÷ 3 = 142.67 → 143 | 143 × 3 = 429 | 0 | **−1 円** 😱 |

最後は残っている原価（428 円）より多く取り崩してしまい、**マイナス 1 円**になった。幽霊どころか、負の値である。金額カラムに負値が入ると、その先の集計や表示が連鎖的に壊れる。

**✅ 総額按分（掛けてから割る）:**

| 売却 | 取り崩しの計算 | 取り崩し | 残口数 | 残取得原価 |
| --- | --- | --- | --- | --- |
| 2 株 | 1000 × 2 ÷ 7 = 285.7 → 286 | 286 | 5 | 714 |
| 2 株 | 714 × 2 ÷ 5 = 285.6 → 286 | 286 | 3 | 428 |
| 3 株 | 428 × 3 ÷ 3 = 428 | 428 | 0 | **0 円** ✅ |

注目してほしいのは、総額按分でも**途中の丸め誤差はゼロではない**ことだ（1 回目の 286 円は実数なら 285.71... 円）。それでも最後はちょうどゼロになる。

なぜか。総額按分の取り崩しは常に「**残っている原価**を口数の比率で分ける」計算だからだ。途中の丸め誤差は消えるのではなく、**残存ポジションの取得原価の中に留まり続け**、最後の売却で「残っている原価の全部」が取り崩されて自動精算される。

誤差を「なくす」のではなく、**誤差の行き場を保証する**。これが総額按分の本質である。

# 「不変条件」としてテストに書く

この性質は、次の**不変条件**（invariant: どんな取引順でも常に成り立つ約束）として言い換えられる。

> 口数がゼロならば、取得原価も必ずゼロ

不変条件は仕様そのものなので、テストに固定しておく。割り切れない数字を意図的に使うのがポイントだ。

```ts
test('割り切れない取得原価でも、全量売却で取得原価はちょうどゼロになる', () => {
	const position = derivePosition([
		buy({ quantity: 3, amount: 100 }), // 1 株あたり 33.33... 円
		sell({ quantity: 3 }),
	]);
	expect(position).toEqual({ quantity: 0, costBasis: 0 });
});

test('分割売却でも誤差は残存ポジション内に留まり、最後にゼロで精算される', () => {
	const position = derivePosition([
		buy({ quantity: 7, amount: 1000 }),
		sell({ quantity: 2 }),
		sell({ quantity: 2 }),
		sell({ quantity: 3 }),
	]);
	expect(position).toEqual({ quantity: 0, costBasis: 0 });
});
```

「150 円になること」のような個別の値のテストと違い、不変条件のテストは実装を総額按分から別の方式にうっかり変えた瞬間に落ちてくれる。**この 2 本は、単価先計算の実装では絶対に通らない。**

# おまけ: 文の順序も仕様の一部

実装はこの 3 行だ。

```ts
const costOut = Math.round((costBasis * tx.quantity) / quantity);
quantity -= tx.quantity;
costBasis -= costOut;
```

按分の分母 `quantity` は「**売却前の**保有口数」でなければならないので、1 行目と 2 行目は**入れ替えられない**。入れ替えると全量売却でゼロ除算になる。

見た目は「計算して、引いて、引くだけ」の素朴なコードだが、行の順序に仕様が埋まっている。こういう箇所こそ、前節のような不変条件テストで守っておくと安心だ（順序を入れ替えるとテストが即座に落ちる）。

# 補足: 税金の計算とは別物

日本の税法には「総平均法に準ずる方法」という取得単価の計算規定があり、単価を**円未満切り上げ**で都度確定する。つまり本記事の「単価を先に丸めるのは悪」という話は、あくまで**アプリ内部の整合性**（口数ゼロ ⇔ 原価ゼロ）の話である。確定申告用の数字が必要な場合は税法の規定に従ってほしい。同じ「移動平均」でも、目的が変われば正しい丸め方も変わる。

# まとめ

- お金は浮動小数点数でなく**最小通貨単位の整数**で持つ。すると丸めの設計が必要になる
- 整数演算では `(a / b) * c` と `(a * c) / b` は**別の式**。丸めてから掛けると誤差が増幅される
- **掛けてから割る（総額按分）**なら、丸め誤差は残存ポジション内に留まり、全量売却で自動精算される
- 誤差をゼロにしようとするのではなく、**誤差の行き場を保証する**設計を考える
- その保証は**不変条件**（口数ゼロ ⇔ 原価ゼロ）としてテストに固定する
